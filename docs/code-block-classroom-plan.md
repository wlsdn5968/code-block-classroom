## 3. 출시 범위

1단계는 회원 정보를 받지 않는다. 그래서 서버·데이터베이스·개인정보 처리가 없고, 콘텐츠 품질에만 집중할 수 있다.

| **단계**           | **넣는 것**                                                                                          | **빼는 것**            | **다음 단계 조건**               |
|--------------------|------------------------------------------------------------------------------------------------------|------------------------|----------------------------------|
| 1단계 MVP          | v4 콘텐츠 전체 이식, 신규 챕터 "AI와 일하는 법"(컨텍스트·MCP·Skills·권한 승인), 진도는 브라우저 저장 | 로그인, DB, 결제, 광고 | 본인과 지인이 끝까지 풀고 피드백 |
| 2단계 계정         | 로그인, 기기를 바꿔도 이어지는 진도, 개인정보 처리방침 페이지                                        | 결제, 광고             | 진도 저장 요청이 실제로 나옴     |
| 3단계 수익화(미정) | 결제 또는 광고 중 선택                                                                               | —                      | 수익화 여부를 먼저 결정          |

## 4. 기술 구성

**추천은 B안이다.** Next.js의 정적 내보내기로 시작하고, 2단계에서 Supabase를 붙여 C안으로 넘어간다. Next.js 문서는 정적 사이트로 시작했다가 나중에 서버가 필요한 기능을 붙이는 방식을 안내한다.

| **안**                              | **구성**                                      | **장점**                                                                                                                           | **단점**                                                                                                   |
|-------------------------------------|-----------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------|
| A. 단일 HTML 유지                   | 지금 파일 그대로 정적 호스팅                  | 가장 빠름. 배울 것 거의 없음                                                                                                       | 챕터가 늘수록 파일 하나가 비대해져 AI가 고치다 다른 곳을 깨뜨리기 쉬움. 로그인 붙이려면 결국 재작성        |
| **B. Next.js 정적 내보내기 (추천)** | Next.js + GitHub + Vercel. 콘텐츠는 별도 파일 | 콘텐츠·화면 부품·실험실을 파일로 나눠 관리. 빌드하면 out 폴더가 생겨 어느 정적 호스팅에도 올릴 수 있음. 나중에 서버 기능 추가 가능 | 정적 내보내기에서는 Server Actions, 쿠키, 요청을 읽는 Route Handler 등을 못 씀. 1단계에는 필요 없는 기능들 |
| C. Next.js + Supabase 처음부터      | B + 로그인·DB                                 | 처음부터 진도 저장                                                                                                                 | 출시 전에 RLS·개인정보 처리방침까지 해야 함. 검증 안 된 수요에 미리 비용을 들임                            |

### 호스팅·DB 요금과 제약 (공식 문서, 2026-10-09 확인)

| **서비스**       | **무료 플랜**                                                                                       | **유료 플랜**              | **이 서비스에 주는 영향**                                                                                                      |
|------------------|-----------------------------------------------------------------------------------------------------|----------------------------|--------------------------------------------------------------------------------------------------------------------------------|
| Vercel           | Hobby: 무료. 월 Fast Data Transfer 100GB, 하루 배포 100회. **비상업·개인 용도만 허용**              | Pro: 개발자 좌석당 월 \$20 | 결제, 상품·서비스 판매 광고, AdSense 같은 광고를 넣으면 상업적 사용이라 Pro 이상 필요. 후원 요청은 상업적 사용에 해당하지 않음 |
| Supabase (2단계) | Free: 프로젝트당 DB 500MB, 월간 활성 사용자 50,000명, 활성 프로젝트 2개, **1주 비활성 시 일시정지** | Pro: 월 \$25부터           | 무료 프로젝트 2개 한도를 다른 사이드 프로젝트와 나눠 써야 함. 공개 서비스가 일시정지되면 로그인이 멈춤                         |

1단계는 Supabase를 쓰지 않아 DB 제약이 없고, 수익을 내지 않는 동안은 Vercel Hobby로 충분하다. 수익화를 하는 순간 Vercel 플랜을 다시 결정해야 한다.

## 5. 콘텐츠 관리와 정확성 원칙

**콘텐츠를 코드에서 분리해 파일로 관리하고, 출처 없는 문장은 빌드가 실패하게 만든다.** '추측 금지'를 사람의 주의력이 아니라 장치로 지키는 방식이다.

### 파일 구조 (제안)

> content/
>
> blocks/ ui.json, server.json … (블록 레슨 9개)
>
> types/ dash.json, game.json … (서비스 유형 7개)
>
> chapters/ ai-work/ … (신규 챕터)
>
> phrases.json (AI 말 번역기)
>
> sources.json (출처 목록)

### 출처 항목에 담을 값

| **필드**   | **뜻**                                     | **예**            |
|------------|--------------------------------------------|-------------------|
| id         | 출처 이름표                                | sbkey             |
| title, url | 문서 제목과 주소                           | Supabase · API 키 |
| kind       | 공식(primary) / 2차(secondary)             | primary           |
| checkedAt  | 마지막으로 원문을 열어 확인한 날           | 2026-10-09        |
| volatile   | 자주 바뀌는 정보인지 (가격, 키 이름, 정책) | true              |

### 검수 규칙 (제안)

1.  모든 설명 단락과 미션 해설은 출처 id를 1개 이상 가진다. 없으면 검사 스크립트가 빌드를 멈춘다.

2.  2차 자료만 있는 내용은 화면에 '2차 자료'로 표시한다. 공식 문서를 찾으면 교체한다.

3.  volatile 출처는 정해둔 주기마다 다시 열어 확인하고 checkedAt을 갱신한다. 주기는 결정 필요 (예: 분기 1회).

4.  비유는 단순화이므로, 실제와 다른 점이 있으면 '실제로는' 문장을 반드시 붙인다.

5.  예시 주소·예시 키·시뮬레이션은 화면에 '예시', '시뮬레이션'으로 표시한다.

6.  AI가 쓴 초안은 사람이 출처 원문과 대조한 뒤에만 합친다(merge).

## 6. 2단계 데이터 설계

**표는 2개만 만들고, 저장하는 개인정보는 로그인에 필요한 것과 닉네임으로 제한한다.** 화면에는 Supabase publishable 키만 두고, 접근 범위는 RLS로 막는다. Supabase 문서는 publishable 키를 웹 페이지에 둬도 되며, RLS가 접근 범위를 정한다고 설명한다.

| **표**   | **칸**                                                                                   | **용도**                    |
|----------|------------------------------------------------------------------------------------------|-----------------------------|
| profiles | id(로그인 계정 id), nickname, created_at                                                 | 화면에 보여줄 이름          |
| progress | user_id, item_id(예: block:ui, type:dash), status(seen/done), correct, total, updated_at | 어떤 레슨을 어디까지 했는지 |

**RLS 규칙**: 두 표 모두 '본인 줄만 읽기·쓰기·지우기'. Supabase는 외부에 열린 모든 표에 RLS를 켜라고 한다.

> alter table progress enable row level security;
>
> create policy "본인 진도만" on progress
>
> for all using ( auth.uid() = user_id ) with check ( auth.uid() = user_id );

### 연결 규칙

- 처음 로그인할 때 브라우저에 저장돼 있던 1단계 진도를 계정으로 옮긴다.

- 회원 탈퇴 시 두 표의 본인 줄을 지울 수 있게 한다. 처리방침에 파기 절차를 적어야 하기 때문이다.

- secret 키는 2단계 기능에 필요 없다. 나중에 서버 기능이 필요하면 그때 정적 내보내기를 풀고 서버에만 둔다.

## 7. 보안·법무 체크리스트

이 서비스가 가르치는 규칙을 서비스 자신도 지킨다. 출시 전에 아래를 모두 체크한다.

### 1단계

- 저장소에 .env가 올라가지 않았는지 확인 (Next.js 기본 템플릿은 .env를 .gitignore에 넣어둠)

- 화면 코드에 실제 키가 없는지 확인. 실험실의 키는 모두 가짜이고 잘려 있어야 함

- 실제 Android·iPhone, 다크 모드에서 모든 버튼 글자가 보이는지 확인

- 수익 요소(결제·광고)가 없는지 확인. 있으면 Vercel Hobby 사용 불가

- 각 문서 내용을 원문 그대로 베끼지 않고, 요약 + 링크 형태인지 확인

### 2단계 (로그인 추가 시)

- 모든 표에 RLS 켜기, 다른 계정으로 남의 진도가 안 보이는지 직접 테스트

- 화면에는 publishable 키만, secret 키는 어디에도 없음

- 개인정보 처리방침 페이지 작성·공개. 개인정보 보호법 제30조는 처리 목적, 처리·보유 기간, 파기 절차·방법, 정보주체의 권리와 행사 방법, 책임자 연락처 등을 포함하라고 정한다

- Supabase 같은 해외 서비스에 데이터를 두는 것과 처리 위탁을 처리방침에 어떻게 적을지 확인. 제30조는 처리 위탁(해당 시)과 대통령령으로 정한 해외 이전 관련 사항을 나열한다

- 처리방침 문안은 개인정보보호위원회 작성지침을 기준으로 하고, 공개 전 법률 전문가 확인을 받을지 결정

제30조 내용은 법제처 국가법령정보센터에 자동 접속이 막혀 있어 2차 자료(위키독스 인용)로 확인했다. 2단계 착수 전 원문을 직접 확인해야 한다.

## 8. 개발 순서

Windows + Git Bash + Claude Code 환경 기준이다. 단계마다 끝나면 커밋하고, 다음 단계는 새 브랜치에서 시작한다. Vercel은 브랜치마다 미리보기 주소를 따로 만들어 주므로, 실제 서비스(main)를 건드리기 전에 확인할 수 있다.

**기존 서비스에 붙이는 경우** 1~4번은 기존 프로젝트 상황에 따라 달라진다. 부록 A의 분석 결과를 보고 결정한다.

### 1단계 MVP

1.  **준비**: GitHub·Vercel 계정, Node.js 설치. Node.js 최소 버전은 Next.js 공식 설치 문서에서 확인한다.

    - 완료 기준: 터미널에서 node -v가 버전을 보여줌

2.  **프로젝트 만들기**: AI에게 "create-next-app으로 프로젝트를 만들고 내 개인 GitHub 계정에 비공개 저장소로 올려줘"

    - 완료 기준: GitHub에 첫 커밋이 보임

    - 확인: .gitignore에 .env가 있는지. GitHub 조직(organization)의 비공개 저장소는 Vercel Hobby로 배포할 수 없으므로 개인 계정에 만든다

3.  **Vercel 연결과 첫 배포**: Vercel 대시보드에서 New Project → 저장소 선택 → Deploy

    - 완료 기준: ….vercel.app 주소가 휴대폰에서 열림

4.  **정적 내보내기 설정**: AI에게 "next.config에 output: 'export'를 추가해줘"

    - 완료 기준: 빌드하면 out 폴더가 생김

5.  **콘텐츠 분리**: v4 HTML을 프로젝트에 넣고 "블록·유형·번역기·출처 데이터를 content 폴더의 JSON으로 옮겨줘. 문장은 한 글자도 바꾸지 마. 출처 없는 항목이 있으면 실패하는 검사 스크립트도 만들어줘"

    - 완료 기준: 검사 스크립트가 통과하고, 출처를 하나 지워보면 실패함

6.  **화면 이식**: 홈 → 블록 레슨 → 실험실 9개 → 서비스 유형 → 번역기 순서로 한 번에 하나씩

    - 확인: 진도 저장(localStorage)은 브라우저에서만 실행되게. Next.js 문서는 빌드 중에는 window·localStorage를 쓸 수 없다고 안내한다

    - 완료 기준: 미리보기 주소에서 v4와 같은 동작

7.  **실제 기기 점검**: Android 1대, iPhone 1대, 다크 모드, 큰 글자 설정

    - 완료 기준: 7장 체크리스트의 1단계 항목 전부 체크

8.  **신규 챕터 'AI와 일하는 법'**: 출처 원문을 먼저 모으고 → 초안 → 원문 대조 순서

    - 완료 기준: 모든 문단에 출처와 확인일

9.  **출시**: main에 합치면 실제 서비스 주소에 반영. 지인에게 공유하고 피드백 수집

### 2단계 계정 (1단계 후 필요가 확인되면)

1.  Supabase 프로젝트 생성, publishable 키만 환경변수로 등록

2.  표 2개와 RLS를 마이그레이션 파일로 만들기. 실행 전에 drop·delete가 없는지 확인

3.  로그인 붙이기, 브라우저 진도를 계정으로 옮기기

4.  다른 계정으로 남의 진도가 안 보이는지 테스트

5.  개인정보 처리방침 페이지 공개 후 출시

## 부록 A. Claude Code 작업 요청서

이 부록은 Claude Code에게 그대로 전달하는 요청이다. 함께 전달하는 파일: 이 문서, code-block-classroom-prototype-v4.html.

### A-1. 요청

내가 지금 만들고 있는 서비스(이 저장소)에 '코드 블록 교실'을 붙이려고 한다. **코드를 고치기 전에** 아래 분석을 먼저 하고, 보고서를 보여준 뒤 내 승인을 받고 진행해 줘.

### A-2. 먼저 분석할 것 (읽기만, 수정 금지)

1.  현재 저장소의 구조: 프레임워크와 버전, 라우팅 방식, 배포 방식(Vercel 여부, 정적 내보내기 사용 여부), 로그인 유무와 방식, 데이터베이스 사용 여부

2.  통합 방식 후보와 각각의 장단점, 기존 코드에 미치는 영향 범위. 예: 기존 앱 안의 하위 경로로 추가 / 같은 저장소의 별도 앱 / 별도 저장소·별도 배포

3.  이 문서 4장의 B안(정적 내보내기)이 기존 서비스와 맞는지. 기존 서비스가 이미 서버 기능을 쓰고 있다면 output: 'export'는 적용하지 말고 기존 방식을 따르는 안을 제시

4.  기존 로그인·DB가 있다면 6장 2단계 설계(profiles·progress 표, RLS)를 기존 것과 어떻게 합칠지

5.  프로토타입의 SRC·B·PH·T·LABS 데이터를 어디에 어떤 형식으로 둘지

### A-3. 지켜야 할 조건

- 콘텐츠 문장은 한 글자도 바꾸지 않는다. 바꿔야 할 문장이 보이면 목록으로 따로 보고한다.

- 출처 id 연결을 유지하고, 출처 없는 항목이 있으면 실패하는 검사 스크립트를 만든다.

- 작업은 새 브랜치나 워크트리에서 한다. main에 직접 커밋하지 않는다.

- secret 키·service_role 키를 화면 코드나 NEXT_PUBLIC\_ 변수에 두지 않는다.

- 새 표를 만들면 RLS를 켠다. 마이그레이션에 drop·delete가 있으면 실행 전에 알린다.

- localStorage 접근은 브라우저에서만 실행되게 한다.

- 버튼·입력칸 글자색을 명시한다. 프로토타입에서 Android 글자 사라짐 버그가 있었다.

- git push --force, rm -rf처럼 되돌리기 어려운 명령은 실행 전에 이유와 함께 묻는다.

- 모르는 것은 추측하지 말고 "확인 필요"로 표시한다.
