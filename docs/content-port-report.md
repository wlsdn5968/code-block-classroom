## 21. 기획서 v2 M1 게임 뼈대 (2026-11-09 작성, 2026-11-10 승인)

- 결정(사용자 승인 "권고대로"): 기획서 12장 7개를 추천대로 — 초등학생은 쉬운 말 기준, 지도는 잠그지 않음, 레벨 이름은 초안대로·마스코트는 나중, 결과물은 수칙 카드 → 질문 꾸러미 순, 통계는 지인 테스트 뒤, 새 지역은 비밀과 개인정보부터, 쉬운 말 다시 쓰기는 챕터 2부터.
- 만든 것: 머리글 레벨 표시, 홈 학습 지도(지역 4·칸 29, ○ 안 감 · ● 답함 · ★ 첫 답에 맞힘, "다음에 할 것"), "내 기록"(레벨·경험치 막대·배지 12·진도 파일 저장/불러오기), 배지 알림. 규칙은 `content/game/levels.json`·`badges.json`, 판정은 `lib/game.ts`, 빌드 전 `scripts/check-game.mjs` 검사.
- 경험치: 첫 답에 맞히면 10, 틀려도 답하면 3(답하면 해설이 열림). M1 최대 440. 배지 "다시 일어서기"는 복습함(M2)이 생기면 열림.
- 저장: 기존 4개 키는 그대로, 새 기록은 `cs-game`(번역기 묶음·사건 6개). 기존 3개 키도 망가진 값·없는 id를 걸러 읽고, 저장 직전에 다시 읽어 다른 탭 기록을 지우지 않게 했다.
- 진도 파일 불러오기는 **합치기**(지금 기록은 지우지 않고 첫 답도 지금 것을 유지). 칸이 빠진 파일은 거부. 서버로 보내지 않음.
- 동등성 검사: 새 요소는 모두 `data-new="game"`이라 비교에서 빠짐 → 시나리오 77개 실패 0. 기존 화면 문장 변경 없음.
- 독립 검토 반영 12건: 불러오기가 기록을 지우던 문제(→ 합치기), 저장값 null이면 화면 멈춤, 다른 탭 기록 덮어쓰기(guess·cguess·finish), 블록 칸 이름이 영어 id, 번역기 칸 누락, "0과 모름" 판정이 시작 상태를 미리 셈, "위험 탐지기" 설명과 판정 불일치, 배지 여러 개 알림, 다운로드 링크 정리, 접근성(결과 문구 role=status, 배지 얻음/아직 숨김 글자, 지금 레벨 표시), 검사 스크립트(챕터 목록을 content에서 읽기, 경험치 순서). 직접 찾은 것: 첫 방문자의 첫 배지 알림이 뜨지 않던 버그, 알림이 해설을 가림(→ 위쪽), 배지 칸 한 줄 배치(→ 두 줄).
- 실측(휴대폰 조건, CPU 4배 느리게): 8바퀴 왕복 메모리 main 4.2→4.5MB, M1 4.3→4.6MB(같은 기울기, 새 누수 없음). 슬라이더 중간값 17~20ms(main 17ms). 받는 파일 41→45개, 압축 전 +69KB. 첫 화면 시간은 이 PC에서 같은 빌드도 2.8~4.8초로 흔들려 비교 불가.
- 검사: 게임 규칙 검사에 일부러 넣은 실수 5종을 모두 잡음. 전 과정 검사에 지도·경험치·배지 9종·진도 파일(저장→지우기→잘못된 파일 거부→불러오기→빈 파일·칸 빠진 파일) 확인 추가, 화면 291곳 문제 0.
- 재검토(2026-11-10, 수정본 대상) 반영 2건: 지도의 번역기 칸이 "전체" 목록으로 가서 칸 상태가 안 바뀌고 "다음에 할 것"이 맴돌던 문제(→ 아직 안 연 첫 묶음으로 이동, 검사 추가), 불러오기의 "새로 더한 기록 수"에 다른 탭 기록이 섞이던 문제(→ 저장값을 먼저 합친 뒤 셈). 타입 검사·빌드·동등성 77개·전 과정 291곳 모두 통과.

## 22. 기획서 v2 M2 내 가방: 복습함·수칙 카드·질문 꾸러미 (2026-11-10, 승인)

### 25-2. 판단

- **검토자**: 문제의 원인이 아니다. 진짜 버그를 잡았다(불러오기가 기록을 지움, 경험치 부풂). 다만 **두 번째 검토는 수확이 작았다**. 그리고 "쉬운가"는 묻지 않고 "사실이 맞는가"만 물었다.
- **반영**: 모자랐다는 기록은 없다. 콘텐츠에서는 **한쪽으로 기울었다**. 기록에 남은 검토 반영은 조건·예외를 더하는 것뿐이고, 글을 줄이거나 쉽게 바꾼 반영은 M4 전까지 없다. 쉬운 말을 재는 검사는 11-10(M4)에야 생겼다. 결과적으로 레슨 11개가 기준을 넘어 다시 쓰게 됐다. (초안이 처음부터 길었는지, 검토로 길어졌는지는 나눠서 확인하지 못함)
- **계획·초안**: 한 PR에 기능·새 문장·검사 확장을 함께 넣어 검토 지적이 한꺼번에 많이 나왔다. 초안을 쓸 때 길이 기준이 없었다.
- **순서**: "승인 → 재검토 → 합치기" 순서라, 재검토에서 고칠 것이 나오면 승인받은 문장이 승인 뒤에 바뀔 수 있는 구조였다. 문서 파일 2개만 바꾼 승인 기록 커밋(`405dcb7`)에도 8분 17초짜리 검사가 돌았다.
- **기다리는 시간**: 검사가 두 배 넘게 길어졌고 PR 하나에 보통 3번(PR 열 때, 수정 뒤, main) 돈다.

  - WebKit 고치기 전: 320~390px에서 둘째 버튼의 숫자가 375~397에 있어 버튼 밖이고 문서 너비 397로 화면이 넘침. 414px에서는 화면은 넘치지 않지만 숫자가 버튼(끝 368) 밖.
  - 고친 뒤: WebKit이 일곱 너비 모두 크롬 계열과 글자 하나까지 같음. 넘침·버튼 밖 0건. 크롬 계열은 고치기 전과 글자 하나까지 같음.
  - 배포 뒤 실제 주소에서 다시 재도 같은 값.
- 검사: 동등성 77개·539회 실패 0, 전 과정 검사 Chromium 348곳 문제 0(이 PC와 실제 주소). WebKit 전 과정 검사는 문제 10건 → 6건(가로 넘침 4건 사라짐, 남은 6건은 30-6의 새로고침 시점 문제).
- 독립 검토(haiku): 측정 파일 대조 맞음, `.mi`는 `Home.tsx`에서만 씀. 414px의 "버튼 밖"을 짚어 반영.
- 바꾸지 않은 것: 비슷한 격자 `.cm`·`.rname`(`1fr`과 `auto`가 같이 있음). WebKit 전 과정 검사 348곳에서 넘침이 나온 곳은 홈 화면뿐이었다. 프로토타입(수정 금지 원본)에는 옛 규칙이 그대로 있다.
