## 2. 운영자 승인을 기다리는 것

운영자에게 물은 것 두 가지:
1. 이 틀(쉬운 설명 → 한 줄 정리 → "더 깊이 보기" 접힘)로 나머지 레슨도 진행해도 되는지

승인되면: 승인 기록 커밋 → 최종본 재검토(독립 검토) → 자동 merge → 실제 주소 확인 → 나머지 레슨으로.

- Node 버전이 세 곳에서 다르다(CI 22, 운영자 PC 24.14.0, Vercel 26.x). 이 차이로 생긴 문제는 기록에 없다.
- 이 PC에서 독립 검토 에이전트 2개와 브라우저 검사를 동시에 돌리면 검사가 시간 초과로 실패한 적이 있다. 무거운 검사는 혼자 돌린다.
- 원격(GitHub)에 이미 합쳐진 브랜치 24개가 남아 있다(2026-11-10. 로컬의 합쳐진 브랜치 16개는 지웠다). 지워도 되고(PR에서 복구 가능) 그대로 둬도 동작에는 영향 없다.

## 5. 일하는 순서 (지금까지 지킨 방식)

1. 상태 확인: `git status`, 열린 PR, 필요하면 실제 주소 검사.
2. 브랜치를 만들어 작업한다(main 직접 커밋 금지).
3. 새 콘텐츠는 공식 문서 원문을 내려받아 인용(`evidence`)을 글자 그대로 대조한다.
4. 타입 검사 → 빌드 → `test:parity` → `test:walk`. 화면은 Playwright로 찍어 직접 본다.
5. 독립 검토(낮은 등급 모델 에이전트, 읽기 전용) → 지적을 코드·원문에서 직접 확인하고 반영.
6. `docs/content-port-report.md`에 절을 추가하고 이 파일을 갱신한다.
7. PR을 만든다. 화면 문장이 새로 생기거나 바뀌면 **자동 merge를 켜지 않고** 미리보기와 함께 운영자에게 보고한다.
8. 승인되면: 승인 기록 → 최종본 재검토 → 자동 merge → 실제 주소에서 확인.

보고할 때는 한 일·검증·확인하지 못한 것·운영자가 할 일(무엇을, 왜, 안 하면, 급한지, 누를 버튼)을 쉬운 말로 적는다.
